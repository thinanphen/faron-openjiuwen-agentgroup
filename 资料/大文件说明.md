### 为什么不上传

GitHub 对 git 仓库有**单文件 100 MB 硬上限**（超过会被服务端直接拒绝，无论用 PAT 还是 OAuth）。
这两个文件分别是上限的 4.8 倍与 1.35 倍。

> **这不是我们独有的处理方式。** 上游 `Legal-Workspace` 的 README 原文写着：
> 「注意 git 单文件上限 100 MiB，故走 **Release 资产**而非仓库文件」
> 本仓库沿用同一实践。

## 三、校验完整性

拿到文件后，用 PowerShell 核对：

```powershell
Get-FileHash -LiteralPath '法元Faron-产品演示-赛事版0.7.3.mp4' -Algorithm SHA256
# 期望：FD48D80CB0758637671FAB637FD603EC235CC7398E2A51366C106EBAD38F80C3

Get-FileHash -LiteralPath '法元_0.7.3_赛事版_x64-setup.exe' -Algorithm SHA256
# 期望：BD3C5349D05C7FE50416E7BD3FF5CFCDA5933CA94DB1E451ED1E2EE07F76F268
```

> ⚠️ **一处待复核的 SHA256 冲突（已建立单一来源）**：
>
> `资料/03-项目计划书/项目计划书.md` 中 0.7.3 安装包登记为 `639F0F93…`，
> 而 `资料/05-移动端与安装说明/说明.md` 与本文件登记为 `BD3C5349…`。
>
> **这条冲突目前无法从文档内部判定谁对** ——
> 计划书自己记载该安装包在 2026-09-14 **当天被重打过**（「重打安装包」+ 更换品牌图标），
> 所以两份登记**可能各自对应不同时间点的构建产物**。
> 两个体积登记（135.16 MB / ≈135.2 MB）实际是同一量级
> （141,735,028 字节 = 135.17 MiB），差异**只在 SHA256**。
>
> **修正做法（原评估文档曾下结论「说明文档正确、计划书写错」，该结论下得太早，已更正）**：
> 1. 取最终提交包内的 `法元_0.7.3_赛事版_x64-setup.exe`
> 2. 执行 `Get-FileHash -LiteralPath '<该文件>' -Algorithm SHA256`
> 3. 把结果写入 **`资料/版本清单.json`**（本目录），并把该条目的
>    `sha256_status` 由 `disputed` 改为 `verified`
> 4. 各文档改为引用 `版本清单.json`，不再各自抄写校验值
>
> **单一来源**：👉 [`版本清单.json`](版本清单.json)——它是唯一权威登记，
> 本文件与计划书里的数值仅供对照。

## 四、如果确实需要把大文件放进 GitHub

GitHub **Release 资产**（不是仓库文件）支持单文件最大 **2 GB**，是可行路径：

```powershell
# 需要 workflow scope 或 repo scope 的 PAT；不能用仓库文件路径，必须走 Release API
curl -X POST -H "Authorization: token <PAT>" `
     -H "Content-Type: application/octet-stream" `
     --data-binary "@法元Faron-产品演示-赛事版0.7.3.mp4" `
     "https://uploads.github.com/repos/<owner>/<repo>/releases/<release_id>/assets?name=faron-demo-0.7.3.mp4"
```

若走这条路，建议把视频**先按赛规重剪到 3 分钟以内**再上传——当前成片 **7 分 13 秒**，
是赛事规定「3 分钟以内」的 **2.4 倍**（详见整改建议文档 G2）。
