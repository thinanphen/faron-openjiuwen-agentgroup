## 三·补 · 材料完整性清单

> **用途**：评委若想核验「我收到的这份包是否被改过」，可拿清单逐文件比对。

| 项 | 值 |
|---|---|
| 清单文件 | [`../资料/提交物清单.json`](../资料/提交物清单.json) |
| 生成方式 | `python tools/gen_manifest.py` |
| 校验方式 | `python tools/gen_manifest.py --check` |
| 条目来源 | **`git ls-files`** —— 即「仓库跟踪的文件」这一权威名单，而非某个目录下的全部文件 |
| 条目数 | **93** |
| 合计体积 | 47,007,526 字节（44.83 MiB） |
| 算法 | SHA256（大写十六进制） |

### 排除项及理由（逐条写明，不默默跳过）

| 排除项 | 理由 |
|---|---|
| `.git` | 版本库元数据，非提交物 |
| `__pycache__` / `*.pyc` | Python 字节码缓存，随解释器版本变化，无核验价值 |
| `runtime/` | 运行产出物（`.docx` / `runlog`），**每次运行都变**，纳入会导致清单永远对不上 |
| `logs/` | openJiuwen 运行期日志；已被 `.gitignore`，不属于提交物 |
| `_hold/` | 本机暂存目录；已被 `.gitignore` |
| `交付补丁/` | 由 `git format-patch` 从提交生成的**交付方式**，不是交付内容 |
| `提交物清单.json` | 本清单自身；自引用无法得到稳定哈希 |
| `.DS_Store` / `Thumbs.db` / `*.swp` / `*.tmp` | 编辑器与系统临时产物 |

### 为什么用 `git ls-files` 而不是目录遍历

**提交物的定义是「仓库跟踪的文件」，不是「某个目录下的所有文件」。**
手写目录清单容易把未跟踪的临时文件误纳 —— 本轮就差点把已被 `.gitignore`
的 `logs/`（6 个运行日志）算进提交物。改用 `git ls-files` 后这类错误从根上消失。

> 清单里记了 `_条目来源` 字段，若某台机器上没有 git，会退回目录遍历并在该字段标明，
> 便于判断清单的可比性。
