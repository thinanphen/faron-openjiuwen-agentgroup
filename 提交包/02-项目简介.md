# 02 · 项目简介

## 一句话

**法元 · Faron** 是一个跑在律师/法务本机的「办案数字员工」——它把「查法规、写文书、问 AI、译外文」
四类散落在浏览器/翻译器/通用 AI 之间的工作收进一个单机应用，并用一段**不经过模型**的确定性规则
保证交付物里每一处法条引用都真实可查。

---

## 我们解决的问题

法律从业者的日常是「查法规、写文书、问 AI、译外文」。现状有三个真痛点：

| 痛点 | 现状 | 后果 |
|---|---|---|
| **工具割裂** | 法规在浏览器、文书在 Word、翻译在另一个 App、AI 又在一个网页 | 上下文反复搬运，效率损耗大 |
| **引用不可信** | 通用 AI 会生成「看起来像法条」的文本，条号可能是编的 | 高风险场景不敢用；律师要逐条人工回查 |
| **数据要出网** | 云端 SaaS 需上传涉密合同 | 律所/企业合规上过不去，直接影响采购决策 |

**法元的选择**：把法库搬到本机、把编排做成 Agent 团队、把「引用是否成立」变成**代码级判定**。

---

## 它现在是什么（不是概念稿）

| 维度 | 事实 |
|---|---|
| **可用产品** | Windows 桌面端已出安装包（约 135 MB，内含预置法库），装机即用 |
| **真实法库** | 内置 **152,940 条**日美官方法条（日本 2,104 部 / 美国法典 53 Title + 宪法），来源 e-Gov / govinfo |
| **文书智能体** | 「小元」支持 **5 类任务**：合同审查 / 起诉状 / 证据目录 / 质证意见 / 代理词 |
| **交付物** | 固定五段式，一键导出 **.docx**（含 Word 原生表格），可打开、可溯源、可二次编辑 |
| **知识图谱** | 案由 → 构成要件 → 请求权基础 / 证据 / 争点，**驱动计划卡编排**（要件不漏、法域自动限定） |
| **引用自检** | **两段确定性校验**，不调用模型，结论可复现、可用反例现场验证 |
| **人在环** | 关键步骤可设人工确认闸门；人有最终裁决权 |
| **数据安全** | 单机 SQLite（WAL + FTS5），数据不出本机；API Key 密文落盘 |
| **用户验证** | **107 份**真实问卷（市场调研） |

## 本届大赛的工作：把「可信」变成可复现的事实

法元原本是自研的四角色线性循环（规划 → 检索员 → 起草员 → 质检员）。
本届我们做了两件事：

### ① 把编排层搬到 openJiuwen 官方 AgentGroup

用 `openjiuwen.agent_teams` 承载团队协同：**6 个成员 / 12 个工具**
（主理 + 检索员 + 图谱策展 + 起草员 + 质检员 + 人类复核员）。

### ② 保留并强化自研的「确定性引用自检」

这是我们认为真正值钱的部分——**框架不解决的那一半问题**：

```
通用 Agent 会说「我查过了」。
在高风险域（法律、医疗、金融），"模型自称查过"不是证据。

法元把「引用是否成立」变成代码级规则判定：
  · 不调用任何模型
  · 结论只依赖 (正文, 工具真实返回集合, 案由图谱)
  · 同样输入永远得到同样输出
  · 因此可以用反例现场验证
```

**实测演示**：我们在起草稿里**故意埋了一个库里不存在的条文号「第9999条」**，
质检环节当场把它点名：

> 本次共 4 处法条引用，其中 1 处未在本次工具真实返回中找到：**「第9999条」**。
> 上述引用不计为有效引用，请人工核实或删除。

这一段**不需要装软件、不需要 API Key**，评委可以本地亲手复现（见下方）。

## 评委零 Key 复现路径（最小成本验证）

```bash
# 零依赖：不需要 openJiuwen、不需要任何 Key
python tests/verify_zero_dep.py
#   → 6 项全通过，末行断言「全程零 openjiuwen import」
```

它会屏蔽全部框架 import 后，重跑两段确定性自检，并证明「第9999条」这类
库外条号被当场点名、而合法引用被正常放行。

## 与 openJiuwen 的能力对应

**已装配**（代码中可核验）：`TeamAgentSpec` / `LeaderSpec` / `TeamMemberSpec` / `TeamRole`
/ `DeepAgentSpec` / `AgentCard` / `enable_hitt` / `model_pool`（`by_model_name`）
/ `StorageSpec(sqlite)` / `TransportSpec(inprocess)` / `enable_permissions`
/ `openjiuwen.core.foundation.tool.tool` / `Runner.resource_mgr.add_tool`

**规划中**（代码中不存在，如实标注）：框架任务板工具与 `send_message` 的真正驱动、
`dispatch_mode="scheduled"`、`enable_swarmflow`、`model_router`、跨进程 `pyzmq`。

> ⚠️ **本作品的装配层已真实验证，运行层尚未跑通多智能体协同闭环**。
> 详见 [`04-技术方案.md`](04-技术方案.md) 的「运行层现状」一节。
