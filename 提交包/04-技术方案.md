# 04 · 技术方案

> **叙事主线**：openJiuwen 的 AgentGroup 解决「一起干活」；法元补上「干得可信」。
> 在涉外法律交付这类高风险场景里，多个 Agent 协同产出的每一处法条引用，
> 都由一段**不经过模型**的确定性规则逐条判定真伪与适用性——
> **评委可以不带任何 API Key，在本地亲手复现这个判定。**

## 四、核心创新：两段确定性自检

### 4.1 它解决什么问题

通用 Agent 会说「我查过了」。在高风险域，**「模型自称查过」不是证据**。

法元把「引用是否成立」变成**代码级规则判定**：

```
正文里的每一处法条引用
    ↓ extract_citation_tokens()   确定性正则（中日文条号 / 日文分条 / 美国法典 §NN）
token 去重
    ↓ article_covers()            归一化后：完全相等，或落在合法条号边界的前缀
【第一段】能否在「本次工具真实返回」中找到 → 未覆盖项点名
    ↓ same_law()                  名称互含即同法（含中英别名）
【第二段】是否落在案由图谱的请求权基础范围内 → 超范围项列出
```

### 4.2 关键性质：纯函数

| 性质 | 说明 |
|---|---|
| **不调用模型** | 结论只依赖 `(正文, 工具真实返回集合, 案由图谱)` |
| **确定性** | 同样输入永远得到同样输出（测试用两个进程 + 随机 hash seed 验证） |
| **可反例验证** | 注入库里不存在的条号，必然被点名（有 9 组定向测试） |
| **零依赖可复现** | `citation.py` / `kg.py` 只用标准库，**不需要 openJiuwen、不需要 Key** |

### 4.3 实测证据

**第一段**（故意埋雷）：

```
第一段结论：1/2 命中，未覆盖 ['第9999条']
```

**第二段**（图谱适用性）：

```
- 本案由图谱请求权基础：民法、美国法典 Title 15 — 商业与贸易、会社法
- 本次引用法条 3 部，落在案由范围内的 3 部
- 全部引用均落在本案由图谱的请求权基础范围内
```

**零依赖验证**（模拟评委干净机器，屏蔽全部 openjiuwen import）：

```
[1] ✓ citation.py / kg.py 在无框架环境下可加载
[2] ✓ 图谱可用：案由=涉外合资经营合同纠纷，要件 5 个，请求权基础 3 部
[3] ✓ 第一段自检可用：1/2 命中，点名 ['第9999条']
[4] ✓ 第二段自检可用：in_scope=['民法']，out_of_scope=[]
[5] ✓ 自检报告可渲染（含未覆盖项点名）
[6] ✓ 全程零 openjiuwen import —— 零依赖承诺成立
```

### 4.4 支持与拒绝的引用形式

| 形式 | 示例 | 判定 | 理由 |
|---|---|---|---|
| 中文/日文条号 | `第百三条` `第五百二十二条` | ✅ 支持 | 主场景 |
| 日文分条 | `第百三条の二` | ✅ 支持 | 日文法条实际写法 |
| 美国法典 | `§1125` `§1125(a)` `§102-1` | ✅ 支持 | **含字母款项**（官方原正则只支持数字款项） |
| 条文更完整 | 工具返 `第一百四十三条第二款`，正文写 `第一百四十三条` | ✅ 命中 | 正当前缀 |
| 款项前缀 | 工具返 `§1125(a)`，正文写 `§1125` | ✅ 命中 | 正当前缀 |
| **少写一位** | 工具返 `§1125`，正文写 `§112` | ❌ **不命中** | 假条号，必须拦住 |
| **半截括号** | `§1125(` | ❌ 不命中 | 不构成完整引用 |

> 后两行是本仓库相对上游实现的**修订**（编号 E9），并已回写建议上游。

### 4.5 对上游实现的修订建议（已回写）

| # | 上游问题 | 现象 | 建议修法 |
|---|---|---|---|
| **G11** | 引用正则漏字母款项 | `(?:\d+)?` 只允许 `(1)`；实测 `'§1125(a)'` → token `'§1125'`，`(a)` 被丢弃 → `§1125(a)` 与 `§1125(b)` 被当成同一处引用 | `\(\d+\)` → `\([0-9a-zA-Z]+\)`（**一行**） |
| **G12** | 图谱法名中英不一致 | 图谱存中文名、法库返英文名，`sameLaw` 名称互含判不出 → 适用性误报 | `kg_node.name_alt` 字段**本就存在**，种子补上英文别名即可（已在本仓库落地） |

### 已修复的一个关键装配缺陷（编号 E1）

开发过程中发现并修复了一处**会让整个多智能体叙事崩塌**的缺陷：

```python
# 错误写法
agents = {"leader": leader, "teammate": retriever}
```

按 openJiuwen 0.1.19 的解析顺序（`agent_configurator.py:965-973`）：

```python
if member_name and member_name in spec.agents:
    return spec.agents[member_name]
return spec.agents.get(role.value) or spec.agents.get("teammate") or spec.agents["leader"]
```

`kg_curator` / `drafter` / `citation_auditor` 的 `member_name` 都不在字典里，
于是**全部落到 `teammate` 兜底**——三个成员运行时拿到的是检索员的 spec 与工具集，
且框架**静默兜底、不报错**。后果：质检员拿不到 `audit_citations`，
「两段自检」这个核心卖点在运行时不存在。

**修复前后实测对比**（`tests/test_assembly.py`）：

| | 修复前 | 修复后 |
|---|---|---|
| 不同 spec 对象数 | **1**（四成员同一对象 id） | **5** |
| `kg_curator` 工具集 | `['law_by_id','laws_country_preview','laws_search']` | `['kg_add_candidate','kg_confirm_edge','kg_find_case','kg_query']` |
| 测试结果 | 5 通过 / 4 失败 | **9 通过 / 0 失败** |

修法与回归防线：按 `member_name` 建 `agents` 字典键，并新增 9 组装配测试永久防回归。

## 八、信息分层：「用户可见面 ↔ 内部机制 ↔ 代码位置」

> **这一节回答一个可能被问到的问题**：为什么产品里**看不到**「自我进化」这个功能？

### 8.1 设计判断

「自我进化」（联邦配方进化）是**真实实现**，但它此前以**一级导航 + 926 行机制页**的形式
暴露给用户：六段管线卡、差分隐私与 K 匿名、加权平均公式、A/B 采纳、RL 对照段。

我们的判断是：**用户需要的不是机制，是「状态 + 控制」。**

| | 团队想讲的 | 律师在买的 |
|---|---|---|
| 对象 | 联邦统计聚合、差分隐私、K 匿名、加权配方 | **越用越顺手** + **我的文书不出本机** |
| 形态 | 机制 | 状态 + 控制 |
| 时间感 | 多轮收敛曲线 | 「它记住了我的习惯」 |

因此我们**主动决定**把它从一级导航撤下，改成**三处隐式触点**，
并把机制与全部边界声明**分层归档**——不是隐藏，是**有设计意图的信息分层**。

### 8.3 「隐式」不等于「删除」——边界声明一条未减

**这是本节最需要被核对的一点。**

从 UI 撤下的每一句，都能在文档里找到落点。可核验：

| 核验项 | 方法 | 期望 |
|---|---|---|
| `docs/12` 边界表述未减少 | grep `差分隐私\|K 匿名\|仿真\|未实现` | **36 处**（改动前 21 处；R5-P0-1 新增 §十一 故增加，**只增不减**） |
| 完整实验台未丢失 | 文件存在且行数 | `src/evolution-lab/EvolutionLab.tsx` **926 行** |
| UI 机制词已清零 | `node scripts/check-ui-copy.mjs` | `views`+`components` 下 **0 命中** |
| 未接入字段仍被如实报出 | 该项由 `unconsumedFields()` 驱动渲染 | `auditPassFloor` / `minSamples` 标 `wired: false` |
| 无数据不渲染状态 | 首页状态行与计划卡标注均设空值门 | 未采纳配方时**整行/整句不出现** |

> **一句话**：我们把「给谁看什么」**主动决定**了，而不是把功能藏起来。
> 用户侧只留「控制 + 状态」；机制、口径与边界声明完整保留在文档与内部实验台里。

### 8.4 为什么这样做对评审是**加分**而不是减分

1. **初赛是材料评审，不是现场点 UI。** 评委看的是提交包与视频；UI 的导航项数量不是评分项。
2. **「隐式」本身是更高级的产品判断。**
   「用户不需要知道联邦学习，只需要感到顺手」——这是一句能被记住的话；
   而一个叫「自我进化」的机制页，恰恰暴露了**产品没想清楚该给谁看**。
3. **原形态有失分风险。** 一个 926 行的机制页里，但凡有一处口径与文档不一致，
   就是把**实现细节**摊开给非技术评审挑错。信息分层消除了这个风险。
