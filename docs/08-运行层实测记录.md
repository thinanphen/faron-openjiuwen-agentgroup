## 一·补、R9 的两个新 bug（都是自己的代码，不赖框架）

### 新 bug A · 用「assistant 回合数」当剧本游标会跳步

自检里加了 `_walk_script()` 把剧本从头空走一遍，直接断言顺序。

## 二、跑通它踩过的五个坑（按遇到顺序）

### 坑 1 · `session=None` → harness 起不来

```
ExecutionError: [123023] deepagent runtime error,
                reason: NativeHarness not started. Call start() first.
Callback execution failed: on_poll_task - no such table: team_task_<suffix>
```

**原因**：`TeamAgent.stream()` → `_coordination.start(session)` 用
`session.get_session_id()` 推导**按会话后缀**的动态表名。传 `None` 就没有 session_id，
表不建、harness 不启动；`no such table` 只是二次故障。
**修法**：传真实的 `openjiuwen.core.session.agent_team.Session(session_id=..., team_id=...)`。

### 坑 2 · 桩返回普通 JSON → ReAct 静默空闲退出

框架请求带 `"is_stream": true`，期望 `text/event-stream`。
只回 JSON 时日志是：

```
[LLM] <<< response: content_len=0, tool_call_count=0
```

随后 `[NativeHarness] phase running -> idle` —— 看起来像"卡住"，其实是**框架什么都没收到**。
**修法**：桩必须实现 SSE（`data: {...}` 块 + `data: [DONE]`）。

### 坑 3 · `create_task` 挂错方法

`TaskCreateTool.invoke` 调的是 `task_manager.add_graph(...)`，**不是 `add(...)`**。
只挂 `add` 时 `create_task` 明明执行了、钩子一次没响。
**修法**：两个都挂。

### 坑 4 · `claim_task` 少一个参数就全废

实测 schema：

```json
{"required": ["task_id", "status"],
 "properties": {"task_id": {...},
                "status": {"enum": ["claimed", "completed"]}}}
```

`status` 是**必填**，取值只有 `claimed` / `completed`。
只给 `task_id` 会被工具直接拒掉。

### 坑 5 · 成员被 pause 后叫不醒（**本轮的阻塞点，未解决**）

`build_team` 完成后，框架对每个成员执行：

```
finalize_member: pausing team member law_retriever; marking READY for next assignment
```

此后成员的协调轮结束、**退订事件**。而唯一能唤醒空闲成员的事件集合是：

```python
# openjiuwen/agent_teams/agent/coordination/handlers/task_board.py
_TEAMMATE_NUDGE_EVENTS = frozenset(
    {TeamEvent.TASK_CREATED, TeamEvent.TASK_UNBLOCKED, TeamEvent.TASK_RELEASED}
)
```

`_publish_task_created()` 把事件发到
`TeamTopic.TASK.build(session_id, team_name)`，而 `InProcessMessager` **不补发历史事件**。

**实测时序**：

| 时刻 | 事件 |
|---|---|
| 5.4 s | `create_task` → `TASK_CREATED` 发布（此时成员订阅尚未建立） |
| 8.0 s | `[law_retriever] coordination starting`（订阅建立，事件已错过） |
| 8.1 s | `finalize_member: pausing`（成员暂停） |
| 19.5 s | 把 `create_task` 延后到此刻重试 → 仍不唤醒（成员已 paused 且退订） |

**已尝试且均无效**：
① 广播 `to="*"`（7 次）；② 定向 `send_message` 给 `law_retriever` / `drafter`；
③ `update_task` 显式指派 assignee；④ 把主理轮询拉长到 24 轮（约 2.5 分钟窗口）；
⑤ 时序错开（建单延后到成员起来之后）。

#### R9 更新的结论：**问题比「事件错过」更深一层**

R9 把 `spawn_teammate` 这条路走通了（成员真被创建、真被启动、任务真指派到它头上），
但 `claim_task` **仍然是 0**。三条决定性证据：

1. **成员从未发起任何模型回合。** 整个 run 里 `[NativeHarness] started` 与
   `[NativeHarness] round_id=1 started` 只出现**一次** —— 是主理的。
   成员只有 `[...] invoke start, role=teammate` → `coordination starting`，
   **没有 round**。桩共收到 36 次请求，全部来自主理。
2. **发给成员的消息从未被消费。** 库里那条
   `to='law-retriever-r9', broadcast=0, is_read=0` —— 一直未读。
3. **成员轮次不推送，事件就无处落地。** 「成员被唤醒」这一步依赖
   `MessageHandler` 走 `_round.deliver_input(...)`；而 round 根本没起来。

**所以真正卡住的不是「事件来得早」，而是「成员的 round 压根没启动」。**
主理走 `TeamAgent.stream()`（会 `enqueue_initial_mailbox_poll` /
`enqueue_initial_task_poll` 并 pump 流），成员走的是 `invoke start` 另一条路。

**下一轮候选**（按可疑度排序，都还没试）：
1. **看成员是不是需要有人消费它的输出流。** `inprocess` 模式下成员是
   `asyncio.create_task` 起的，若其 `stream()` 的输出没人迭代，round 可能不会被 pump。
   查 `spawn_manager._spawn_teammate_inner` 里那个 task 到底跑的是什么。
2. `dispatch_mode="scheduled"` —— Leader 显式排期，可能走完全不同的启动路径。
3. 去掉 `predefined_members`，让 `build_team` 时**一个成员都不预建**，
   全部靠 `spawn_teammate`（本轮已证明 spawn 本身可用）。
4. 直接读 `agent_teams/agent/coordination/` 下 `round` 的启动条件，
   找到「什么情况下成员的 round 会被 begin」。

## 五、环境级故障：`NO_PROXY` 里的 `[::1]` 让所有 OpenAI 调用失效

**这是本轮最有价值的发现之一，因为它改变了「零成功记录」的归因。**

现象：

```
openjiuwen.core.common.exception.errors.FrameworkError:
[181001] model call failed, reason:
openAI API async stream error: InvalidURL: Invalid port: ':1]'
```

**根因链**：

1. `openai` 3.29.0 改用 `httpx2`（`Requires-Dist: httpx2<3,>=2.12.0`）
2. `httpx2` 在 `AsyncClient.__init__` 里把**代理映射的每个键**当 URL 模式解析：
   ```python
   self._mounts = { URLPattern(key): ... for key in proxy_map }
   ```
3. 代理映射来自 `_get_proxy_map()`，它把 `NO_PROXY` 的**每一项**变成键
4. 本机 `NO_PROXY = .ustc.edu.cn,localhost,127.0.0.1,::1,[::1]`
5. `[::1]`（带方括号的 IPv6）解析出非法端口 → 抛 `InvalidURL`

**四组对照实验**：

| `NO_PROXY` | 构造 `openai.AsyncOpenAI` |
|---|---|
| `.ustc.edu.cn,localhost,127.0.0.1,::1,[::1]` | ❌ `InvalidURL: Invalid port: ':1]'` |
| `.ustc.edu.cn,localhost,127.0.0.1,::1`（去掉 `[::1]`） | ✅ |
| 清空 | ✅ |
| `localhost,127.0.0.1` | ✅ |

**与 base_url 无关**：默认端点、`https://api.openai.com/v1`、本地桩，**6/6 全崩**。

> **这条的意义**：在有这个 `NO_PROXY` 的机器上，**即使配上真 Key 也发不出任何请求**。
> 所以「`run_online.py` 零成功记录」的真因很可能不是缺 Key，而是这个环境变量。
> **修法**：把 `NO_PROXY` 里的 `[::1]` 去掉（`run_stub_online.py` 已自动修正）。

另需 `pip install aiosqlite`（框架任务板初始化必需，此前 `requirements.txt` 未列）。

# 九、R10：把唤醒链逐层切开，找到真正的死点

> **方法**：`tools/apply_wake_probes.py`（只加 `team_logger.info`，**不改任何分支与返回值**）。
> 每层一个探针，跑一次只看一层，逐层收窄。
> **结论先行**：成员从来不是"被唤醒失败"，而是 **`NativeHarness._prepare()` 里
> 卡死不返回** —— 它的协调内核根本没走到"开始接线"那一步。

## 9.1 完整因果链（每一环都有日志实证）

```
成员 spawn
  └─ TeamAgent.invoke()                       ← 有日志 [x] invoke start
       └─ CoordinationKernel.start()          ← 有日志 [x] coordination starting
            ├─ await sess_mgr.bind_session()  ← 探针 STEP1：6 个成员都过了
            ├─ await TeamHarness.start()
            │    ├─ await child.pre_run()          ← TH_PROBE 过了
            │    └─ await NativeHarness.start()
            │         └─ await self._prepare()
            │              └─ await ensure_initialized()   ← ❌ 6 个成员全部卡死在这里
            │                 （NH_PROBE step0 之后再无 step1）
            ├─ await event_bus.start()        ← 永远到不了
            └─ enqueue_initial_task_poll()    ← 永远到不了
```

**因为它卡在 `_prepare()`：**

1. `EventBus` 从未 start ⇒ 成员的 poll 定时器不会起；
2. `enqueue_initial_task_poll()` / `enqueue_initial_mailbox_poll()` 从未执行；
3. `TaskBoardHandler._nudge_idle_agent` 一次都没被调用；
4. 成员永远不会发模型请求（桩 36 次请求全来自主理）；
5. 发给成员的定向消息在库里一直 `is_read=0`。

## 9.2 六条实证（每次都是单独一次 run）

| 层 | 探针 | 判据（实测） |
|---|---|---|
| 1 | `NUDGE_PROBE`（`_nudge_idle_agent` teammate 分支） | **0 条** ⇒ 根本没走到筛选条件，**不是 `board_tasks` 为空** |
| 2 | `DELIVER_PROBE`（`deliver_input` 的 `harness is None`） | **0 条** ⇒ 不是投递被丢 |
| 3 | grep `error in wake_callback` | **0 条** ⇒ handler 没抛异常（该处本来就会 `team_logger.exception`） |
| 4 | `DISPATCH_PROBE`（EventBus 派发） | `POLL_TASK`=11、`POLL_MAILBOX`=11，但 **`INITIAL_POLL_TASK` = 0** |
| 5 | `BUS_PROBE`（`event_bus.start()` 前打 `id`/`is_running`） | **只有主理一条**；`EventBus[leader] starting` 也只一条 ⇒ **成员从未 start 自己的 bus** |
| 6 | `STEP1..STEP5` + `TH_PROBE` + `NH_PROBE` | 主理 step0→step6 全通；**6 个成员只到 `NH_PROBE step0`** |

> **第 6 条是决定性的。** 之前所有猜测（`board_tasks` 空、`assignee` 不匹配、
> 事件时序、投递语意）**全部被这六条排除**。

## 9.3 为什么前七轮都看不见

三个**静默返回**叠在一起，且都在"看起来正常"的位置：

| 位置 | 行为 |
|---|---|
| `kernel.start()` | `if self._event_bus is None: return`（但成员这行没触发，反而更隐蔽——它卡在下面） |
| `on_initial_task_poll` | `if not member_name or task_manager is None: return` |
| `_nudge_idle_agent` | `if not board_tasks: return` |
| `deliver_input` | `if harness is None: return` |

前三个都会让人往"条件不匹配"的方向查；而真正的死点是一个 **`await` 永不返回**——
它不报错、不打日志、不让出任何堆栈，**唯一的表现就是"什么都没发生"**。

> **教训（已写成 D23）**：`await` 卡死的排查价值高于任何 `if` 分支。
> 当一件事"完全没有日志"，先怀疑"卡在某个 await"，而不是"某个条件没满足"。

## 9.4 下一轮候选（针对 `ensure_initialized()`）

死点已收窄到 **`NativeHarness._prepare()` → `await self.ensure_initialized()`**。
下一步只需在 `ensure_initialized()` 内部再切几刀（同样只加日志），候选怀疑点：

1. **它是否在等一个只有主理才有的资源**（模型客户端预热 / skill 可见性扫描 / workspace 锁）。
   实测成员启动时恰好有一条 `[ImageModalityProbe] image modality probed` 只对主理出现，

# 十一、R11-B：**找到了** —— `init_workspace()` 缺顶层标记，六个 agent 反复建目录

> **这是十一轮里第一个"改一行代码就看见效果"的发现。**
> **结论：`_prepare()` 卡死已解决**（6/6 成员全部通过）。
> **但 `claim_task` 仍为 0** —— 新的瓶颈换成了并发写库与桩连接。

## 11.1 怎么找到的

R11 已把死点收到 `NativeHarness._prepare()` → `ensure_initialized()`。
本轮在 `DeepAgent._ensure_initialized()` 里插了 6 个步进探针（`INIT_PROBE k0..k5`）：

| 角色 | 探针轨迹 |
|---|---|
| 主理 | `k0 → k1 → k2 → k3 → k4 → k5` ✅ 全通 |
| **5 个成员** | `k0 → k1 → k2 before init_workspace (needed=True)` → **停住** ❌ |

**卡在第 2 个 await 之后、第 3 个之前的 `await self.init_workspace()`。**

> 坦白：我原本最怀疑的是下一个 `_resolve_read_image_multimodal()`（那条
> `[ImageModalityProbe]` 日志只对主理出现过）。**猜错了** —— 探针一插就知道，
> 这也是"先加日志再猜"的价值。

## 11.2 根因（读源码即可确认）

```python
async def init_workspace(self) -> None:
    ...
    if self._deep_config and self._deep_config.workspace:
        root = Path(self._deep_config.workspace.root_path)
        if (root / ".workspace").exists():      # ← 靠这个文件短路
            return
        builder = DirectoryBuilder(...)
        await builder.build(self._deep_config.workspace.directories)   # ← 卡在这
```

实测 `runtime/stub-workspace` 顶层**没有 `.workspace`**（只有各子目录里有）：
`agents/`、`memory/`、`context/`、`skills/`、`todo/`、`messages/`、`coding_memory/`
各自都有 `.workspace`，**唯独根目录没有**。

⇒ 那个 `exists()` 短路永远不命中 ⇒ **每个 agent 都完整跑一次 `DirectoryBuilder.build()`**。
6 个 agent 对**同一个工作区根**并发建目录 / 写 `AGENT.md` 等模板文件，
Windows 文件锁争用 → 第一个（主理）建完，其余**无限等待**。

## 11.3 修复（改在我们自己的代码里，不动 site-packages）

`run_stub_online.py`：启动前预置工作区标记。

```python
marker = ws / ".workspace"
if not marker.exists():
    marker.write_text("1", encoding="utf-8")
```

**这不是绕过检查**：框架把这个文件当作"工作区已初始化"的**正式约定**
（子目录用的就是同一套约定，内容 1 字节）。预置后所有 agent 在 `exists()` 处直接返回。
