## 一·补、R9 的两个新 bug（都是自己的代码，不赖框架）

### 新 bug A · 用「assistant 回合数」当剧本游标会跳步

`spawn_teammate` 之后框架会**多插一条 assistant 消息**，于是回合数一步跳 2，
游标直接**越过 `create_task`**。现象是「剧本里明明有 create_task，日志里却没执行」，
而且看起来像「create_task 回归失败了」——极难归因（本轮在这上面浪费了一整轮实跑）。

**修法**：改成按「某个工具已被调用过几次」推进（`_call_counts` + `_next_step`）。
多插几条 assistant 都不影响，同名工具重复出现也能正确区分。
自检里加了 `_walk_script()` 把剧本从头空走一遍，直接断言顺序。

### 新 bug B · `member_name` 不能用下划线

```
Invalid member_name 'law_retriever_r9': must start with a lowercase ASCII letter (a-z),
followed by lowercase letters, digits (0-9) or hyphen (-); no uppercase, underscore, ...
```

规则在 `agent_teams/tools/tool_permissions.py::_MEMBER_NAME_PATTERN`。
用下划线时 `spawn_teammate` 直接被拒 → 成员不存在 →
`create_task` 的 `assignee` 校验也跟着失败（**两个工具都「执行了但没落地」**，
轨迹里一条都记不到，非常像「钩子坏了」）。

**修法**：`law_retriever_r9` → `law-retriever-r9`。

## 二、跑通它踩过的五个坑（按遇到顺序）

### 坑 1 · `session=None` → harness 起不来

```
ExecutionError: [123023] deepagent runtime error,
                reason: NativeHarness not started. Call start() first.
Callback execution failed: on_poll_task - no such table: team_task_<suffix>
```

**原因**：`TeamAgent.stream()` → `_coordination.start(session)` 用
`session.get_session_id()` 推导**按会话后缀**的动态表名。传 `None` 就没有 session_id，
表不建、harness 不启动；`no such table` 只是二次故障。
**修法**：传真实的 `openjiuwen.core.session.agent_team.Session(session_id=..., team_id=...)`。

### 坑 2 · 桩返回普通 JSON → ReAct 静默空闲退出

框架请求带 `"is_stream": true`，期望 `text/event-stream`。
只回 JSON 时日志是：

```
[LLM] <<< response: content_len=0, tool_call_count=0
```

随后 `[NativeHarness] phase running -> idle` —— 看起来像"卡住"，其实是**框架什么都没收到**。
**修法**：桩必须实现 SSE（`data: {...}` 块 + `data: [DONE]`）。

### 坑 3 · `create_task` 挂错方法

`TaskCreateTool.invoke` 调的是 `task_manager.add_graph(...)`，**不是 `add(...)`**。
只挂 `add` 时 `create_task` 明明执行了、钩子一次没响。
**修法**：两个都挂。

### 坑 4 · `claim_task` 少一个参数就全废

实测 schema：

```json
{"required": ["task_id", "status"],
 "properties": {"task_id": {...},
                "status": {"enum": ["claimed", "completed"]}}}
```

`status` 是**必填**，取值只有 `claimed` / `completed`。
只给 `task_id` 会被工具直接拒掉。

### 坑 5 · 成员被 pause 后叫不醒（**本轮的阻塞点，未解决**）

`build_team` 完成后，框架对每个成员执行：

```
finalize_member: pausing team member law_retriever; marking READY for next assignment
```

此后成员的协调轮结束、**退订事件**。而唯一能唤醒空闲成员的事件集合是：

```python
# openjiuwen/agent_teams/agent/coordination/handlers/task_board.py
_TEAMMATE_NUDGE_EVENTS = frozenset(
    {TeamEvent.TASK_CREATED, TeamEvent.TASK_UNBLOCKED, TeamEvent.TASK_RELEASED}
)
```

`_publish_task_created()` 把事件发到
`TeamTopic.TASK.build(session_id, team_name)`，而 `InProcessMessager` **不补发历史事件**。

**实测时序**：

| 时刻 | 事件 |
|---|---|
| 5.4 s | `create_task` → `TASK_CREATED` 发布（此时成员订阅尚未建立） |
| 8.0 s | `[law_retriever] coordination starting`（订阅建立，事件已错过） |
| 8.1 s | `finalize_member: pausing`（成员暂停） |
| 19.5 s | 把 `create_task` 延后到此刻重试 → 仍不唤醒（成员已 paused 且退订） |

**已尝试且均无效**：
① 广播 `to="*"`（7 次）；② 定向 `send_message` 给 `law_retriever` / `drafter`；
③ `update_task` 显式指派 assignee；④ 把主理轮询拉长到 24 轮（约 2.5 分钟窗口）；
⑤ 时序错开（建单延后到成员起来之后）。

#### R9 更新的结论：**问题比「事件错过」更深一层**

R9 把 `spawn_teammate` 这条路走通了（成员真被创建、真被启动、任务真指派到它头上），
但 `claim_task` **仍然是 0**。三条决定性证据：

1. **成员从未发起任何模型回合。** 整个 run 里 `[NativeHarness] started` 与
   `[NativeHarness] round_id=1 started` 只出现**一次** —— 是主理的。
   成员只有 `[...] invoke start, role=teammate` → `coordination starting`，
   **没有 round**。桩共收到 36 次请求，全部来自主理。
2. **发给成员的消息从未被消费。** 库里那条
   `to='law-retriever-r9', broadcast=0, is_read=0` —— 一直未读。
3. **成员轮次不推送，事件就无处落地。** 「成员被唤醒」这一步依赖
   `MessageHandler` 走 `_round.deliver_input(...)`；而 round 根本没起来。

**所以真正卡住的不是「事件来得早」，而是「成员的 round 压根没启动」。**
主理走 `TeamAgent.stream()`（会 `enqueue_initial_mailbox_poll` /
`enqueue_initial_task_poll` 并 pump 流），成员走的是 `invoke start` 另一条路。

**下一轮候选**（按可疑度排序，都还没试）：
1. **看成员是不是需要有人消费它的输出流。** `inprocess` 模式下成员是
   `asyncio.create_task` 起的，若其 `stream()` 的输出没人迭代，round 可能不会被 pump。
   查 `spawn_manager._spawn_teammate_inner` 里那个 task 到底跑的是什么。
2. `dispatch_mode="scheduled"` —— Leader 显式排期，可能走完全不同的启动路径。
3. 去掉 `predefined_members`，让 `build_team` 时**一个成员都不预建**，
   全部靠 `spawn_teammate`（本轮已证明 spawn 本身可用）。
4. 直接读 `agent_teams/agent/coordination/` 下 `round` 的启动条件，
   找到「什么情况下成员的 round 会被 begin」。

## 五、环境级故障：`NO_PROXY` 里的 `[::1]` 让所有 OpenAI 调用失效

**这是本轮最有价值的发现之一，因为它改变了「零成功记录」的归因。**

现象：

```
openjiuwen.core.common.exception.errors.FrameworkError:
[181001] model call failed, reason:
openAI API async stream error: InvalidURL: Invalid port: ':1]'
```

**根因链**：

1. `openai` 3.29.0 改用 `httpx2`（`Requires-Dist: httpx2<3,>=2.12.0`）
2. `httpx2` 在 `AsyncClient.__init__` 里把**代理映射的每个键**当 URL 模式解析：
   ```python
   self._mounts = { URLPattern(key): ... for key in proxy_map }
   ```
3. 代理映射来自 `_get_proxy_map()`，它把 `NO_PROXY` 的**每一项**变成键
4. 本机 `NO_PROXY = .ustc.edu.cn,localhost,127.0.0.1,::1,[::1]`
5. `[::1]`（带方括号的 IPv6）解析出非法端口 → 抛 `InvalidURL`

**四组对照实验**：

| `NO_PROXY` | 构造 `openai.AsyncOpenAI` |
|---|---|
| `.ustc.edu.cn,localhost,127.0.0.1,::1,[::1]` | ❌ `InvalidURL: Invalid port: ':1]'` |
| `.ustc.edu.cn,localhost,127.0.0.1,::1`（去掉 `[::1]`） | ✅ |
| 清空 | ✅ |
| `localhost,127.0.0.1` | ✅ |

**与 base_url 无关**：默认端点、`https://api.openai.com/v1`、本地桩，**6/6 全崩**。

> **这条的意义**：在有这个 `NO_PROXY` 的机器上，**即使配上真 Key 也发不出任何请求**。
> 所以「`run_online.py` 零成功记录」的真因很可能不是缺 Key，而是这个环境变量。
> **修法**：把 `NO_PROXY` 里的 `[::1]` 去掉（`run_stub_online.py` 已自动修正）。

另需 `pip install aiosqlite`（框架任务板初始化必需，此前 `requirements.txt` 未列）。

## 七、下一轮该从哪下手（给接手的人）

**核心问题已从「事件错过」收敛为一句**：
**成员的 coordination round 从来没启动过**（只有 `coordination starting`，
没有 `[NativeHarness] round_id=… started`；消息 `is_read=0` 一直未读）。

按可疑度排序：

1. **查成员输出流有没有人消费。** `inprocess` spawn 把成员起成
   `asyncio.create_task`（见 `agent_teams/agent/spawn_manager.py::_spawn_teammate_inner`）。
   若那个 task 跑的是成员的 `stream()` 而**没有任何人迭代它的输出**，
   round 可能就不会被 pump —— 主理是因为驱动脚本在 `async for` 它才转起来的。
   这是目前最像的一条。
2. **`dispatch_mode="scheduled"`** —— Leader 显式排期，可能走完全不同的启动路径。
3. **去掉 `predefined_members`**，`build_team` 时一个成员都不预建，
   全部靠 `spawn_teammate`（R9 已证明 spawn / assign / 启动本身都可用）。
4. 直接读 `agent_teams/agent/coordination/` 里 round 的**启动条件**，
   定位「成员在什么条件下才会 begin 一轮」。
5. 若以上都不行：**如实接受「主理侧已跑通」的现状**，把成员协同标注为未完成，
   不要伪造轨迹。工单 §二 2.3 与 R9 §三 的红线都在这里。
