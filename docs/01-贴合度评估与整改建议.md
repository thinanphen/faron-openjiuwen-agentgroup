### 2.3 三个真实亮点（应当在材料中被放大）

1. **确定性引用自检**——交付物合成与质检由**执行器代码**把正文中的条文引用（中文/日文「第X条（之Y/のY）」、美国法典「§NN」）逐条与「本次工具真实返回的法条」比对，未覆盖项**自动点名**。**不依赖模型自述**，因此可用反例现场验证。
2. **知识图谱驱动规划**——本地知识图谱（案由 → 构成要件 → 请求权基础/证据/争点）先命案由，再生成计划卡，**避免要件遗漏、自动限定法域**；任务真实命中的法条登记为低置信度候选边，人工确认后才作为后续规划依据。
3. **可验收交付闭环**——固定五段式交付物 + 零依赖 OOXML 导出 **.docx**（含 Word 原生表格）+ 任务与文书自动归档 + API Key 密文落盘 + 离线可跑。

### 3.2 方向挂靠判断

**结论：挂靠「🏢 办公」，理由是充分的。**

- 「法元」做的正是**文档处理 + 流程自动化 + 知识管理**三件事的交叉：法规知识库（知识管理）→ 文书智能体端到端起草（流程自动化）→ .docx 交付（文档处理）。与官方办公方向示例**逐条对得上**。
- 同时具备官方**未列举**的加分想象空间：法律是**强合规、强溯源**的垂直域，恰好是通用 Agent 最容易翻车的地方。「法元」的确定性引用自检回答了「Agent 如何在高风险域建立可信」这一通用问题——属于「探索更多创新场景」的正当区间。
- ⚠ **不要**同时勾选「Coding」或「设备互联」（悬浮球是辅助形态，不足以支撑设备互联叙事；多勾会稀释定位）。
- ✅ 建议：**主选「办公」**，在技术方案中把「可扩展为法域 × 文书场景平台」作为复用性论证，而不是第二方向。

### 3.3 与官方推荐的差距

官方明确「**推荐使用 openJiuwen 社区的 AgentOS 平台：WorkSwarm**」。我在源码、文档、演示站中检索 `openJiuwen`／`openjiuwen`／`WorkSwarm`／`jiuwenswarm`／`AgentOS`，**命中数全部为 0**。

这是**本次评估中权重最高的失分项**：不是「做得不够好」，而是「与主办方生态零交集」。评审专家来自 openJiuwen 社区，这一项的观感影响会超出其字面权重。

### 8.1 G11 · 引用自检正则的 `§NN(n)` 覆盖缺口

**官方实现**（`src/lib/agent.ts` 第 610–611 行）：

```js
/第[0-9〇零一二三四五六七八九十百千万]+条(?:(?:之|の|ノ)[0-9〇零一二三四五六七八九十百千万]+)?|§\s*\d+(?:[.\-]\d+)?(?:\(\d+\))?/g
```

**实测行为**（Python `re` 与 JS `matchAll` 语义一致，均为全局非重叠匹配）：

| 输入 | 抽出 token |
|---|---|
| `Under §1125 the claim stands.` | `§1125` |
| `Under §1125(a) the claim stands.` | **`§1125`**（`(a)` 未纳入） |
| `See §101-1 and §362.` | `§101-1`、`§362` |

**后果**：`§1125(a)` 与 `§1125` 经 `normArticleNo` 归一化后都是 `"§1125"`，
**两处引用被当成同一处**（去重后只算 1 处）。对「同一法条不同款项」这种
高频引用形式，自检粒度偏粗。

**影响方向是偏严**——`§9999` 之类依然会被如实点名，不会漏报编造条号；
但「引对了法条、引错款项」这种情况自检发现不了。

**修法建议**（二选一）：

```js
// 方案 A：把款项并入捕获（保留候选）
/第[...]+条(?:(?:之|の|ノ)[...]+)?|§\s*\d+(?:[.\-]\d+)?(?:\([0-9a-zA-Z]+\))*/g

// 方案 B：显式捕获条号与款项两段，规范化时保留款项
/§\s*(\d+)(?:[.\-]\d+)?((?:\([0-9a-zA-Z]+\))*)/g
```

> ⚠ 注意：现正则里 `(?:\(\d+\))?` 只允许纯数字款项（`(1)`），
> 但美国法典实务中更常见的是 `(a)` 这类字母款项——**这才是漏掉的真正原因**。
> 若只把 `\d+` 改成 `[0-9a-zA-Z]+` 即可覆盖 `(a)`，属于**一行修复**。

### 8.2 G12 · 图谱法名与法库篇名的中英不一致，导致适用性校验误报

第二段自检 `auditApplicability` 用 `sameLaw`（名称互含即同法）判定
「引用是否落在案由图谱的请求权基础范围内」。

但两侧命名口径不同：

| 来源 | 名称 |
|---|---|
| 图谱种子（`db.rs` KG_SEED） | `美国法典 Title 15 — 商业与贸易`（中文） |
| 法库返回（`laws.title`） | `United States Code, Title 15`（英文） |

两者互不包含 → **被误判为「超范围」**。

**实测表现**（本轮端到端演示的真实输出）：

```
- 本案由图谱请求权基础：民法、美国法典 Title 15 — 商业与贸易、会社法
- 本次引用法条 3 部，落在案由范围内的 2 部
- 以下引用不在本案由图谱范围内（可能仍然相关，请人工判断）：「United States Code, Title 15」
```

「可能仍然相关，请人工判断」这句兜底文案说明团队**已经预见到**这类情况，
但把本该自动对上的情况推给人判断，会稀释第二段自检的价值。

**修法建议**：`kg_node` 表**已经有 `name_alt` 字段**（表结构第 306–315 行），
但种子播种时从未填入。建议：

1. 给图谱法条节点补英文别名：`name="美国法典 Title 15 — 商业与贸易"`，
   `name_alt="United States Code, Title 15"`；
2. `sameLaw` 改为同时比对 `name` 与 `name_alt`；
3. 或更彻底：把图谱法条节点直接改用**法库规范篇名**（英文），中文名放 `name_alt`。
